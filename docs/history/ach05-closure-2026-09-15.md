# ACH-05 closure — 2026-09-15

ACH-05 ships a non-punitive record of renewed training consistency on the
protected Achievements page. It derives the evidence from immutable completed
session events and introduces no migration, backfill or second frontend request.

## Product behavior

- A comeback starts only after 14 full local-calendar days without a completed
  workout.
- It is recognized on the third distinct active date inside an inclusive
  14-day window beginning on the return date. Multiple sessions on one date
  count once.
- Each recognition keeps the return date, recognition date, inactive-day count,
  active-day count and the third return session as its source.
- The read scans the 500 most recent completed-session events, returns at most
  the 20 newest recognitions and discloses when older history was outside the
  scan.
- The UI explains that time away does not erase the work of returning, shows an
  honest empty state, and links a recognition back to its source session.

## Verification

The production backend health endpoint returned 200, and the protected
Achievements route returned the expected 401 without a bearer token. Railway,
Vercel and all three repository CI workflows were green.

The repository's full `ui:regression` could not run from the isolated frontend:
the saved browser state belongs to `localhost:3000`, while the owner's active
server held that port, and the local backend's CORS policy correctly rejected
the isolated `localhost:3001` origin. A targeted authenticated, read-only smoke
used that saved session, the real local backend auth flow and a browser-injected
ACH-05 response. Both themes at 320, 768, 1024 and 1440 px showed the criteria,
recognition evidence and session link with no horizontal overflow or console
errors.

An authenticated production read remains unverified. The localhost Supabase
state is not portable to the Vercel-protected production app: it resolved to a
null production session and cleared only the temporary routing marker. No
credential was available in the shared browser, so no owner data was changed or
fabricated. In particular, the production account's real recognition count and
the production empty/populated state were not observed.
