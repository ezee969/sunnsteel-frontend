# ACH-08 closure — 2026-09-16

ACH-08 brings the complete earned achievement ledger to member profiles. It is
separate from the six curated ACH-03 slots: the new section always represents
the authoritative current rank, every earned milestone and the bounded comeback
history the viewer is allowed to see.

## Product behavior

- Owner, follower and public access use the existing private-by-default
  `achievements` visibility rule. The backend resolves that access before it
  reads achievement data.
- The profile projection contains the current non-regressing Renaissance rank,
  earned milestones and comeback recognitions. It deliberately excludes next
  rank requirements and next-milestone progress, which stay on the owner's
  `/achievements` page.
- Earned rows preserve honest provenance: an earning date and source session
  when one exists, or `Recognized from history` after reconciliation.
- Comeback rows retain their evidence window and completion date. Source-session
  navigation is exposed only on the owner's profile.
- A denied viewer sees an explicit private state and receives no achievement
  payload. An allowed viewer with no earned data sees an honest empty state.

## Verification

The isolated backend gate passed lint, types, 174 tests, build and compiled
module import. The isolated frontend gate passed lock validation, lint, types,
335 tests across 58 files and a production build. No build ran in the owner's
active checkout or against its running development server.

An authenticated browser flow ran on the public production alias. Supabase token
refresh, backend verification and the app session-marker request all returned
200. The authenticated member endpoint returned `viewerAccess.achievements =
true`, rank `Artisan`, 21 earned milestones and zero comeback recognitions. The
payload contained neither next-rank details nor milestone progress, and the
owner profile rendered the same complete ledger.

A fresh signed-out context opened `/members/eze-prof`. The endpoint returned
`viewerAccess.achievements = false` with no achievement payload, and the page
rendered `Achievements are private.` No account setting or achievement data was
changed by the verification.

The owner profile passed 14/14 focused layout cases: light and dark themes at
320, 390, 430, 768, 1024, 1280 and 1440 pixels. Every case kept exactly one
visible h1, matched document and viewport widths and produced no console error.
Representative mobile, tablet and desktop captures plus the signed-out private
state were inspected visually.

## Not verified

- The full 409-case `ui:regression` suite was not run against production because
  it includes mutating workout flows and assumes the local portfolio seed. The
  complete local sweep also remains unsuitable while the unrelated sustained-run
  Prisma transaction expirations documented by ACH-03 are unresolved.
- This account keeps achievements private, so a follower-visible or
  public-visible ledger was not exercised manually. Backend privacy tests cover
  both allowed branches and the production authenticated member read confirmed
  the positive payload.
- The production account had no comeback recognitions, so a comeback row was not
  observed in browser. Its bounded projection and presentation are covered by
  backend and frontend tests.
