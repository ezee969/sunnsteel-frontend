# ACH-04 closure — 2026-09-15

ACH-04 ships understandable progress toward the fixed achievement catalog on
the protected Achievements page. The delivery reuses the authoritative totals
already assembled by the existing achievement read and introduces no migration,
backfill or second request.

## Product behavior

- The page shows exactly one next fixed milestone in each of the five catalog
  categories, in stable catalog order rather than by proximity.
- Every active row states the exact current value and target. It does not use a
  percentage bar or deadline.
- A category whose finite catalog is exhausted says "All milestones recorded"
  instead of fabricating another target.
- Training-volume copy treats the value as cumulative history and keeps load
  selection subordinate to the training plan.
- Streak evidence uses the best recorded run, not an implied live streak, and
  explicitly keeps recovery days compatible with progress.

## Production verification

The authenticated owner page showed 48 of 50 sessions, 553 of 1,000 completed
sets, every fixed volume milestone complete, 22 of 25 personal-record exercises
and a best 16 of the next 20 training days.

Both themes rendered without page or section overflow, clipped milestone text,
console warnings or console errors at 320, 375, 390, 430, 768, 1024, 1280 and
1440 px. Every size retained one page heading and all five milestone rows. The
production browser pass was read-only. The first development API read
reconciled the already-earned immutable achievement events from existing
history, as designed; no account, workout, profile or preference data was
changed.

The complete local `ui:regression` coverage passed 395/395 across recovery
runs. The first run passed 280 cases, failed six Achievements layouts when the
old sequential reconciliation exceeded its five-second transaction, and did
not reach the final 109 cases. After the batching fix, the 115-case recovery
passed 113; its two failures were environmental: the backend was restarting for
the 320 px light case, and concurrent ROUT-11 imports reached the active
frontend before their newer contract was installed for the 768 px light case.
Both exact cases then passed against the isolated frontend and backend with a
fresh saved session. No layout assertion failed.
